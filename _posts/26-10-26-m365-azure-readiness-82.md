E5 샌드박스 테넌트를 "이 상태로 운영에 들어간다면 무엇이 문제인가"라는 관점에서 점검했다. 영역은 다섯 가지로 나눴다.

| 영역 | 점검 항목 | 결과 요약 |
|---|---|---|
| 관리자 권한 | PIM 활성·적격 할당, 게스트 역할 | 전역 관리자 영구 활성 할당 존재, 게스트에 역할 2개 할당됨 |
| 인증 | 보안 기본값, 조건부 액세스, MFA 등록 | 보안 기본값만 사용 중, CA 정책 0개, MFA 등록자 소수 |
| 외부 협업 | 게스트 초대, Teams 외부 액세스, 회의 로비, SPO 공유 | 전 항목이 가장 포괄적(허용) 기본값 그대로 |
| 감사·데이터 보호 | 진단 설정, Purview 감사, 보존 정책, Lockbox | 진단 설정 없음, 감사 레코딩 미시작, 보존 정책 0개 |
| 운영 | 라이선스, 메시지 센터 | E5 17/25 할당, Entra ID P2 0/1, 메시지 센터 475건 |

마스킹 표기: 테넌트 이름·사용자 UPN·개체 ID·Request/Correlation ID·IP 주소는 이미지에서 검은 박스로 처리했다. 비상 접근 계정 `breakglass01`은 [이전 글](/iam/sandbox-break/)에서 다룬 실습용 계정이라 그대로 뒀다.

## 1. 관리자 권한 — PIM 할당 현황

### 활성 할당

Entra 관리 센터 → Privileged Identity Management → Microsoft Entra 역할 → 할당의 **활성 할당** 탭이다.

![PIM 활성 할당](/assets/images/m365-readiness-82/01-pim-active.jpg)

| 역할 | 활성 할당 | 비고 |
|---|---|---|
| 디렉터리 읽기 권한자 | 서비스 사용자 1 (`Microsoft.Azure.Syn…`) | Microsoft 기본 서비스 주체 |
| 전역 관리자 | 사용자 3 (`Break Glass 01` 포함) | 전원 **영구** 할당 |
| 청구 관리자 | 사용자 1, 서비스 사용자 1 (`Microsoft-Develope…`) | 영구 할당 |

비상 접근 계정이 영구 활성인 것은 의도한 구성이다. 문제는 일반 관리 계정까지 전역 관리자 **영구 활성**으로 남아 있다는 점이다. P2 라이선스가 있는 테넌트라면 일상 계정은 적격(Eligible)으로 내리고 필요할 때만 활성화하는 게 PIM을 쓰는 이유다.

### 적격 할당

![PIM 적격 할당](/assets/images/m365-readiness-82/02-pim-eligible.jpg)

적격 할당에는 전역 관리자로 `Break Glass 01` 하나만 있다. 구성이 거꾸로 됐다. 비상 계정은 활성(영구)이어야 하고, 일상 관리 계정이 적격이어야 한다. 적격·활성 할당의 차이와 비상 계정이 활성이어야 하는 이유는 [비상 접근 계정 글](/iam/sandbox-break/)에 정리했다.

> 조치 과제: 일상 관리 계정의 전역 관리자 할당을 영구 활성 → 적격으로 전환. 비상 계정의 중복 적격 할당은 제거.

### 역할이 할당된 게스트

사용자 목록을 훑다가 **게스트 계정에 역할 2개가 할당된 것**을 발견했다.

![역할이 할당된 게스트 계정](/assets/images/m365-readiness-82/03-guest-ga.jpg)

- 사용자 유형: 게스트, B2B Collaboration 외부 사용자
- 할당된 역할: **2**
- MFA 상태: 인증 방법 2개 등록됨

외부 테넌트에 홈을 둔 계정에 디렉터리 역할이 들어가 있으면, 이 테넌트의 보안 수준이 상대 테넌트의 계정 보안에 종속된다. 실습 편의로 개인 계정을 초대해 권한을 준 상황이라면 운영 전에는 반드시 회수하거나 내부 전용 관리 계정으로 대체해야 한다.

## 2. 인증 — 보안 기본값만 있고 CA가 없다

### 보안 기본값

테넌트 속성 화면이다. **"조직이 보안 기본값으로 보호됩니다"** 상태다.

![보안 기본값 사용 중](/assets/images/m365-readiness-82/04-security-defaults.jpg)

### 조건부 액세스 정책 0개

![조건부 액세스 정책 없음](/assets/images/m365-readiness-82/05-ca-none.jpg)

조건부 액세스 정책은 하나도 없다. 보안 기본값과 조건부 액세스는 동시에 쓸 수 없으므로, 지금 상태 자체가 모순은 아니다. 다만 Entra ID P2가 있는 테넌트에서 보안 기본값에 머무는 것은 라이선스를 쓰지 않는 선택이다.

| | 보안 기본값 | 조건부 액세스 |
|---|---|---|
| 라이선스 | 무료 | P1 이상 |
| 제어 단위 | 테넌트 전체 일괄 | 사용자·앱·위치·디바이스별 |
| 예외 처리 | 불가 | 가능 (비상 계정 제외 등) |
| 레거시 인증 차단 | 포함 | 정책으로 구성 |

운영 전환 시나리오는 명확하다. CA 정책(관리자 MFA 필수, 레거시 인증 차단, 비상 계정 제외)을 **보고 전용**으로 먼저 만들어 영향 범위를 확인한 뒤, 보안 기본값을 끄면서 정책을 켠다. 순서를 반대로 하면 보호 공백이 생긴다.

### MFA 등록 현황

인증 방법 → 사용자 등록 세부 정보 화면이다.

![MFA 등록 세부 정보](/assets/images/m365-readiness-82/06-mfa-registration.jpg)

다단계 인증 가능 사용자는 `Break Glass 01`(Authenticator 앱 푸시)과 관리 계정(패스키 + Authenticator) 둘뿐이다. 나머지 샘플 사용자 전원이 **다단계 인증 불가능** 상태다. 보안 기본값은 사용자에게 MFA 등록을 유도하지만, 등록 전까지는 암호만으로 로그인된다는 뜻이다. CA 전환 시 "MFA 필수" 정책을 켜기 전에 등록 캠페인으로 등록률부터 올려야 잠금 사고가 없다.

## 3. 외부 협업 — 전부 기본값(가장 포괄적)이다

### 게스트 초대 설정

External Identities → 외부 협업 설정이다.

![외부 협업 설정](/assets/images/m365-readiness-82/07-guest-invite.jpg)

| 항목 | 현재 값 | 평가 |
|---|---|---|
| 게스트 사용자 액세스 제한 | 디렉터리 개체 속성·멤버 자격으로 제한 (중간) | 무난 |
| 게스트 초대 제한 | **조직 내 모든 사용자(게스트·비관리자 포함)가 초대 가능** — 가장 포괄적 | 운영 부적합 |
| 셀프 서비스 등록 | 아니요 | 무난 |

게스트가 게스트를 초대할 수 있는 상태다. 운영에서는 최소한 "멤버 권한이 있는 사용자만" 또는 "특정 역할만"으로 내려야 초대 경로가 추적된다.

### Teams 외부 액세스

Teams 관리 센터 → External access 설정이다.

![Teams 외부 액세스 설정](/assets/images/m365-readiness-82/09-teams-external.jpg)

- 외부 도메인: **Allow all external domains**
- 관리되지 않는(개인) Microsoft 계정과의 채팅·회의: **On**, 외부 발신 새 채팅 수신까지 허용
- 평가판 테넌트와의 통신: Off

모든 도메인 허용 + 개인 계정 수신 허용 조합은 피싱 접점이 가장 넓은 상태다. 운영에서는 허용 도메인 목록 방식으로 바꾸거나, 최소한 개인 계정발 신규 채팅 수신은 꺼야 한다.

### 회의 참가·로비

![회의 참가 및 로비 설정](/assets/images/m365-readiness-82/10-teams-meeting-lobby.jpg)

- 익명 사용자의 회의 참가: **On** (확인 없이)
- 로비 우회 대상: **조직 구성원과 게스트**
- 로비 입장 허가: 주최자·공동 주최자·발표자

익명 참가 허용 자체는 외부 협업에서 흔한 선택이지만, 익명 참가 On + 로비 우회에 게스트 포함 조합이면 링크만 있으면 회의 내용에 닿는 범위가 넓어진다. 회의 성격에 따라 로비 우회를 "조직 구성원만"으로 좁히는 걸 검토할 항목이다.

### SharePoint·OneDrive 기본 공유 링크

SharePoint 관리 센터 → Policies → Sharing이다.

![SPO 기본 공유 링크 설정](/assets/images/m365-readiness-82/11-spo-default-link.jpg)

- 기본 링크 유형: **Anyone with the link**
- 기본 권한: **Edit**
- Anyone 링크 만료: **설정 안 됨**

이 조합이 이번 점검에서 가장 위험한 기본값이다. 사용자가 공유 버튼을 누르면 기본으로 **로그인 없이 누구나 편집 가능한 무기한 링크**가 만들어진다. 운영 전환 시 기본 링크는 "Specific people"로, Anyone 링크를 유지해야 한다면 만료일과 보기 전용을 강제해야 한다.

### OneDrive 보존

![OneDrive 보존 설정](/assets/images/m365-readiness-82/12-onedrive-retention.jpg)

삭제된 사용자의 OneDrive 보존은 기본값 **30일**이다. 퇴사자 데이터 인계 프로세스가 30일 안에 끝나지 않는 조직이라면 늘려야 한다(최대 3650일). 라이선스 미보유 계정은 60일째 읽기 전용, 93일째 보관 처리된다는 안내도 함께 표시된다.

## 4. 감사·데이터 보호 — 로그가 남지 않는 상태

### Entra 진단 설정 없음

![진단 설정 없음](/assets/images/m365-readiness-82/08-diag-settings.jpg)

Entra ID 진단 설정이 **하나도 정의되어 있지 않다**. SignInLogs·AuditLogs를 비롯한 30종 가까운 로그 카테고리를 Log Analytics·스토리지·Event Hubs로 내보낼 수 있지만, 아무것도 내보내지 않는 상태다. Entra 포털의 로그인 로그는 기본 보존이 30일(P2 기준)이라, 그 이상의 보존·상관 분석이 필요하면 진단 설정으로 내보내야 한다.

### Purview 감사 미시작

Purview → Audit 화면에서 **"Start recording user and admin activity"** 배너가 떠 있다.

![Purview 감사 미시작](/assets/images/m365-readiness-82/13-purview-audit.jpg)

감사 레코딩이 켜져 있지 않으면 사용자·관리자 활동이 기록되지 않고, 사고 조사 시점에 켜도 과거는 소급되지 않는다. 테넌트를 만들면 보통 자동으로 켜지지만 이 테넌트는 꺼져 있었다. **점검 중 가장 먼저 눌러야 하는 버튼**이다.

### 보존 정책 0개

![보존 정책 없음](/assets/images/m365-readiness-82/14-retention-none.jpg)

Data Lifecycle Management의 보존 정책도 0개다. 메일·Teams 대화·SharePoint 문서가 사용자 삭제만으로 사라질 수 있는 상태다. 규제 요건이 있는 조직이라면 워크로드별 보존 정책이 운영 전 필수 항목이다.

### 고객 Lockbox 미사용

![고객 Lockbox 설정](/assets/images/m365-readiness-82/15-lockbox.jpg)

M365 관리 센터 → 조직 설정 → 보안 및 개인 정보의 고객 Lockbox는 **체크 해제** 상태다. Microsoft 지원 엔지니어가 조직 데이터에 접근할 때 승인을 요구하는 기능으로 E5에 포함되어 있다. 켜는 데 비용이 들지 않으므로 E5 테넌트라면 켜 두는 쪽이 기본값이어야 한다.

## 5. 운영 — 라이선스와 변경 공지

### 라이선스 현황

![라이선스 현황](/assets/images/m365-readiness-82/16-licenses.jpg)

| 제품 | 할당 | 사용 가능 |
|---|---|---|
| Microsoft 365 E5 Developer SKU V2 (without Windows and Audio) | 17/25 | 8 |
| Microsoft Entra ID P2 | 0/1 | 1 |

Entra ID P2 단품 1개가 **미할당**으로 남아 있다. [1주차 글](/iam/m365-sandbox-week1/)에서 동적 그룹 기반 자동 할당을 실습하고 원복한 흔적이다. E5에 이미 P2가 포함되어 있으므로 기능 공백은 없지만, 운영 테넌트라면 미할당 라이선스는 비용 정리 대상이다.

### 메시지 센터 475건

![메시지 센터](/assets/images/m365-readiness-82/17-message-center.jpg)

메시지 센터에 **475개 항목**이 쌓여 있다. Teams 신기능, Viva Insights 기본값 변경, Defender for Office 365 격리 동작 변경처럼 "관리자 영향·사용자 영향" 태그가 붙은 공지가 섞여 있다. 운영에서는 이걸 사람이 전부 읽는 게 아니라 Planner 동기화나 서비스별 필터로 관리 루틴을 만들어야 한다. 변경 공지를 안 읽어서 기본값 변경을 놓치는 것도 이번 점검에서 본 "기본값 그대로" 문제의 원인 중 하나다.

## 6. 점검 자동화 — Graph 앱 권한 구성

화면을 하나하나 여는 점검과 별개로, Graph API로 같은 항목을 읽는 앱 `readiness-audit-app`을 등록했다. 인증서 기반 app-only 구성은 [이전 글](/iam/m365-graph-app-only/)과 같은 방식이다.

![readiness-audit-app API 권한](/assets/images/m365-readiness-82/18-app-api-permissions.jpg)

Microsoft Graph 애플리케이션 권한 9종에 관리자 동의까지 완료한 상태다. 전부 **Read 계열**로만 구성했다.

| 권한 | 읽는 것 |
|---|---|
| `Application.Read.All` | 앱 등록·서비스 주체 (과도 권한 앱 점검) |
| `AuditLog.Read.All` | 감사·로그인 로그 |
| `Group.Read.All` | 그룹 (동적 그룹·역할 할당 그룹) |
| `Organization.Read.All` | 테넌트 정보·라이선스(subscribedSkus) |
| `Policy.Read.All` | CA 정책·인증 방법 정책·보안 기본값 상태 |
| `RoleManagement.Read.Directory` | 디렉터리 역할 할당 (PIM 포함) |
| `ServiceMessage.Read.All` | 메시지 센터 공지 |
| `User.Read.All` | 사용자 전체 프로필 (게스트·역할 보유자 식별) |
| `User.Read` (위임) | 로그인 사용자 기본 프로필 |

이 권한 조합이면 이번 점검의 1·2·5장(권한·인증·운영)은 전부 스크립트로 떠낼 수 있다. Teams·SharePoint 관리 설정은 Graph만으로 부족해서 각 관리 셸이 따로 필요한데, 거기서 아래 오류를 만났다.

## 7. 점검 중 만난 로그인 오류 2건

### AADSTS50197 — 사용자를 찾을 수 없음

![AADSTS50197 오류](/assets/images/m365-readiness-82/19-err-50197.jpg)

```
AADSTS50197: Sorry, we could not find the user, please sign-in again.
```

삭제·복원을 반복했던 테스트 계정으로 로그인할 때 발생했다. 브라우저에 남은 이전 세션 쿠키가 삭제된 사용자 개체를 가리키는 상태라, 세션을 정리하고(InPrivate 또는 로그아웃 후) 다시 로그인하면 해소된다. 계정을 지웠다 다시 만드는 실습 테넌트에서 자주 만나는 오류다.

### 530035 — 디바이스 미등록 상태에서 접근 차단

![530035 오류](/assets/images/m365-readiness-82/20-err-530035.jpg)

```
Error Code: 530035
앱 이름: MS Teams Powershell Cmdlets
디바이스 플랫폼: Windows 10
디바이스 상태: Unregistered
```

Teams PowerShell 모듈로 관리 셸에 접속하는 과정에서 "정상적으로 로그인되었지만 이 리소스에 액세스할 수 있는 권한이 없습니다"로 차단됐다. 세부 정보에 **디바이스 상태: Unregistered**가 찍혀 있다. 530035는 디바이스 조건을 요구하는 보안 정책에 미등록 디바이스로 접근할 때 나오는 차단 코드다. 점검용 VM이 테넌트에 등록되어 있지 않아 발생했고, 디바이스를 Entra 등록(또는 조인)하거나 등록된 관리 단말에서 접속하면 통과한다. 관리 도구 접근에 디바이스 조건이 걸려 있는지는 문서가 아니라 이렇게 차단 로그로 확인하게 되는 경우가 많다.

## 정리 — 운영 전환 전 조치 목록

| 우선순위 | 항목 | 현재 → 목표 |
|---|---|---|
| 1 | Purview 감사 | 미시작 → 레코딩 시작 (소급 불가, 즉시) |
| 2 | 게스트 디렉터리 역할 | 역할 2개 할당 → 회수, 내부 관리 계정으로 대체 |
| 3 | SPO 기본 공유 링크 | Anyone·Edit·무기한 → Specific people, Anyone 링크 만료 강제 |
| 4 | 전역 관리자 활성 할당 | 일상 계정 영구 활성 → 적격 전환 (비상 계정만 영구 활성) |
| 5 | 조건부 액세스 | 정책 0개 → 보고 전용으로 생성·검증 후 보안 기본값과 교체 |
| 6 | MFA 등록 | 소수 등록 → 등록 캠페인으로 등록률 확보 후 MFA 필수 정책 |
| 7 | 게스트 초대 범위 | 전원 초대 가능 → 멤버 이상 또는 특정 역할로 제한 |
| 8 | Teams 외부 액세스 | 전 도메인 허용 → 허용 목록 방식 검토, 개인 계정 수신 차단 |
| 9 | Entra 진단 설정 | 없음 → SignInLogs·AuditLogs를 Log Analytics로 내보내기 |
| 10 | 보존 정책·Lockbox·미할당 라이선스 | 각각 생성·활성화·정리 |

샌드박스라서 전부 기본값이어도 문제가 없었지만, 같은 상태의 테넌트가 운영이라면 1~3번은 점검 당일 조치 대상이다. 다음 글에서는 `readiness-audit-app`으로 이 점검 항목들을 스크립트화해서, 화면 캡처 없이 같은 결과를 떠내는 과정을 정리할 예정이다.
